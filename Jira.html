h3. Restrict block/unblock actions on work packages to authorized teams (role-based access control)

Following the PRIME unblock Codes discussion (6/18 meeting; related to PRIM-922), the Project Revenue team has identified a governance gap in the work package blocking functionality.

Because projects can no longer be reopened once fully closed under the new SAP-driven closure process, teams use the work-package block function to stop further time and expense activity without permanently closing a project. The Billing team's inability to reopen closed projects can leave WIP unresolved and leave closed projects with remaining balances thus they are utilizing the blocking feature instead. Blocking and unblocking are currently immediate actions with no approval workflow, and anyone with system access can unblock a work package. This risks work packages being unblocked by mistake or without authorization, allowing additional time and expenses to be charged and undermining audit traceability.



This story covers implementing role-based access control so that unblock actions are limited to designated teams, supporting audit tracking and reducing the risk of unauthorized or accidental changes.

 h2. Summary

Calls that go through Informatica (SavePIF, AcceptChange, CallInformaticaSAPAPI) hung from about 10:57 PM on 8 Oct 2026 until the app restarted at 6:38 AM on 9 Oct 2026. Other pages worked normally.

h2. Evidence

* 10:44:16 PM: An exception from Informatica was logged when creating a new token.
* 10:45 PM to 6:38 AM: zero completed calls to Informatica. A typical nigh would be 100- 200 calls.
* Stalled requests ran past 56 minutes, longer than every HTTP timeout (100 s for tokens, 10 min for Informatica).
* Calls resumed right after the restart.

h2. Root Cause

Think of the token code as a single key to a shared room. Before anyone gets a new key from the front desk, the code hangs a "Key being made, please wait" sign on the door. Everyone else sees the sign and waits. When the key is ready, the sign comes down.
The problem: if something went wrong while making the key (a network hiccup, a bad response), the code crashed before it reached the line that takes the sign down. The sign stayed up forever, so every later request kept waiting for a key that was never coming. Nobody could get in until the whole application was restarted.

h2. Proposed Fix

Wrap the key-making in a try/finally, which means "no matter what happens, even if it crashes, always take the sign down at the end." If the key-making fails, that one request still gets its error, but the next request is free to try again instead of waiting forever.
